# 只有一個插座 · 第二版可玩原型

下班前的 180 秒，工作陸續進來。房間網路壞了，玩家必須用唯一的插座，在電腦、手機與風扇之間安排供電，盡可能準時交件。

沿用 TypeScript + Vite + HTML/CSS；繁體中文、CSS 設備圖形、無後端或外部 API。提示音由 Web Audio 產生，無外部字型、圖片或音效依賴。

## 安裝與啟動

需要 **Node.js 22.18 以上，建議 Node 24**。先確認 `node --version`。

本機已安裝 Node 24.6.0；若仍顯示 Node 10，Vite 會出現 `SyntaxError: Unexpected token {`，請先切換：

```powershell
nvm use 24.6.0
node --version
npm install
npm run dev
```

開啟終端機顯示的網址，通常為 `http://localhost:5173/`。已有 lockfile 的乾淨安裝可使用 `npm ci`。

`nvm use` 會切換電腦目前使用的 Node 版本；若權限不足，請用系統管理員終端機執行。IDE 仍顯示舊版時，重新開啟終端機。其他電腦可先執行 `nvm install 24.6.0`。`.nvmrc` 記錄專案版本，nvm-windows 請明確指定 `nvm use 24.6.0`。

```sh
npm test          # 遊戲邏輯、生成器與策略檢查
npm run balance   # 30 個固定種子的供電策略報告
npm run test:browser # Chrome 介面驗證與加速完整一局
npm run build     # TypeScript 檢查與正式建置
npm run preview   # 預覽正式建置
```

瀏覽器測試使用本機 Chrome。Windows 若只有 Edge，可執行 `$env:BROWSER_CHANNEL = 'msedge'` 後再跑 `npm run test:browser`。測試自行啟動 localhost:5183，結束後關閉；截圖存於已忽略的 `test-results/`。Playwright 僅供開發測試，不進入遊戲發布檔案。

## 操作與交件流程

1. **手機接收**：在工作卡的通知按「手機接收」。手機有電即可，不必插電。電腦尚未選取工作時，接收會自動選取這件。
2. **電腦處理**：點工作卡或「選取處理」切換工作，並供電給電腦。一次只處理一件；切換任務、拔掉電腦插頭都保留進度。
3. **手機上傳**：處理完成後，按「上傳交件」。上傳完成才得分；上傳期間可讓通電的電腦處理另一份工作。

- 點設備，或按 **1 電腦 / 2 風扇 / 3 手機**，切換唯一的供電對象。
- 按 **Q / W / E** 選取對應的已接收工作，卡片左上角有按鍵標記。未接收通知仍需按「手機接收」；上傳仍需按「上傳交件」。每份工作保留自己的快捷鍵直到結案，新工作補入空位，其他工作不會改綁按鍵。桌機也保留對應欄位。
- 開始後切換為精簡遊玩版面，收起大型設備插圖；供電按鈕、倒數、電量與效率固定在上方，捲動工作卡時仍可操作。卡片不因倒數改變而自動排序。
- 按「暫停」、空白鍵或 Escape 暫停；按「繼續上工」恢復。鍵盤選取按鈕後可用 Enter 操作。
- 切換瀏覽器分頁會暫停**所有**期限、生成、處理、上傳、溫度與電量；返回後需手動繼續。
- 音效由開始按鈕啟用，按「音效：開／關」切換。只在事件發生時播放短音，不持續鳴叫。

### 限時工作

- **重要程度用醒目分數表示**：一般委託（未滿 100 分，綠色）、重要委託（100～149 分，藍色）、關鍵委託（150 分以上，紫色）。目前各工作分別為 60、80、110、150、180 分；文字與數字也能辨認等級。
- 「急件」和橘色期限警告表示時間壓力；可比較高分關鍵工作與快到期的小件，自行決定優先順序。
- 卡片新增「立即優先做：估計餘裕／超時」，把目前效率的剩餘處理、現有上傳排隊及自己的上傳時間合併估算，並考慮下班時間。假設手機有電、立刻接收與優先處理，不含補電、降溫、操作反應及其他電腦工作的等待；手機沒電時改提示先充電。
- 工作區顯示「尚未入帳」總分（待上傳與上傳中），提醒哪些成果還需要完成交件。手機電量不足以完成單件剩餘上傳時，會提示建議邊充邊傳。

- 狀態為：待接收 → 待處理 → 處理中 → 待上傳 → 上傳中 → 已交件。未通電時顯示處理暫停；手機沒電時顯示上傳暫停。
- 工作**通知到達就開始倒數**，不接收也會逾期。卡片顯示報酬、期限、處理／上傳進度、目前效率下的剩餘處理時間。
- 同時最多 3 件未結束任務，包含待接收、待上傳及上傳中；同時最多一份急件。
- 最快到期的卡片有標記；剩 10 秒變色、最後 5 秒柔和閃爍，遵循瀏覽器的減少動態效果偏好。
- 玩家可放棄任何未結束工作，立即釋放位置。逾期／放棄不會結束整局。
- 上傳途中仍有期限；逾期立即取消上傳。恰好在期限或下班時完成的上傳算成功交件。
- 已交件、逾期、放棄的工作移出工作區，保存在「本局紀錄」。
- 漏件通知與紀錄會保留結案時的階段：尚未接收、處理到幾 %、完成處理但未上傳、或上傳還剩幾秒；若當時手機關機，也會標明。這是當時狀態，不代表推斷出唯一失敗原因。

### 手機與風扇的取捨

- 手機不插電時待機耗電，上傳另加耗電；插電時可邊充邊上傳，電量仍會回升。
- 手機沒電不能接收或開始上傳；正在上傳的工作保留進度，復電後自動續傳。
- 關機時的新通知仍佔工作位置、期限繼續走；畫面顯示關機提示與保留通知，復電後才能查看內容和接收。
- 風扇通電降溫；電腦實際處理時每秒升溫 0.3°C，沒有處理（包含斷電與完成待上傳）時每秒僅升溫 0.08°C。28°C 以下效率 100%，每升高 1°C 減少 6.5 個百分點，最低 35%；沒有進度損毀或隨機故障。
- 高溫時可選擇直接搶交快完成的工作，或先降溫、為後續較長工作保留效率；待機空檔升溫較慢，也可以拿來補電。
- 卡片上的處理估計以**目前效率**推算，假設電腦持續通電；不包含未來溫度變化、充電、降溫或排隊時間，上傳時間另列。

### 下班結算

180 秒時統一結算：成功交件數、漏件數、總分、歷史最高分。

結算另列漏件發生的階段，特別標出「處理完成卻未交出」的件數；可展開逐件進度回顧。逾期、放棄與下班未完成均涵蓋在內，成功交件不列入漏件回顧。重新開始會清空回顧。

**總分 = 已交件報酬加總 − 漏件數 × 40**，分數可為負。漏件包含逾期、放棄、下班未完成，每件只扣一次。
歷史最高分與靜音設定保存在 localStorage；儲存不可用時仍可遊玩並保留本次頁面中的最高分。

「再挑戰一次」完整重設任務、時間、溫度、電量、供電、選取、上傳、通知、紀錄及生成器，只保留最高分和音效偏好。

## 任務安排與固定種子

第 1 秒送來「修改簡報」，第 24 秒送來「校對文案」，先熟悉接收、處理、上傳。第 40 秒後開始混合任務：到達間隔 11～17 秒，第 100 秒後縮為 9～14 秒。

工作區滿時，生成器每 2 秒再試一次，**沒有背景堆積的工作佇列**。臨近下班只挑選能保留完整期限、且正常處理與上傳後還有 6 秒操作餘裕的任務。這保證新工作個別有正常完成時間，不保證多件重疊時都來得及。

一般遊玩每局使用新種子。開發時在網址加上 `?seed=42` 可重現固定種子，例如 `http://localhost:5173/?seed=42`。頁尾顯示本局種子；固定種子下重開會使用同一種子。因工作區是否滿會影響生成時機，重現同一局也需要相同操作。

## 重要平衡參數

所有遊戲數值集中在 `src/config.ts`。

`importance.important`／`importance.critical` 管理重要程度分數門檻，`slackWarning` 管理交件餘裕的吃緊提示。`workingHeatPerSecond`／`idleHeatPerSecond` 區分工作與待機升溫。本次調整熱度規則，沿用任務報酬與計分方式，也保留既有最高分；不同熱度版本的成績不宜當作嚴格的難度比較。

| 單局／工作區容量 | 180 秒／3 件 |

| 工作升溫／待機升溫／風扇降溫 | 每秒 +0.3／+0.08／−1.4°C |

## 程式結構

- `src/config.ts`：數值與任務模板。
- `src/generator.ts`：固定種子亂數、任務到達節奏、容量與急件限制。
- `src/game.ts`：純遊戲狀態、接收／處理／上傳、唯一結案入口與固定步進。
- `src/main.ts`：操作接線、遊戲生命週期、分頁暫停。
- `src/view.ts`、`src/devices.ts`：畫面與原有設備圖形；工作卡按 ID 保留 DOM，倒數不會重建按鈕。
- `src/style.css`、`src/work.css`：原有視覺與第二版工作區、響應式排版。
- `src/preferences.ts`：最高分、音效偏好與簡短提示音。
- `src/review.ts`：結案進度文字與漏件階段統計；`src/game.ts` 在結案時保存獨立快照。

## 驗證與試玩重點

自動規則測試涵蓋完整交件流程、斷電／切換保留進度、手機關機／恢復、並行上傳、逾期取消、重複結算防護、暫停與重開、30／60／144 FPS 一致性、生成容量與急件限制。

Chrome 介面測試以加速時鐘跑完 seed 42 的 180 秒，交件 8 件、漏件 3 件、630 分；另驗證暫停、模擬分頁事件、關機通知、充電恢復、重開、儲存，以及 320／390px 無水平溢出。截圖可在 `test-results/` 查看。音效是否舒適、真實切換分頁及 itch.io iframe 的行為仍需人工確認。

精簡版面另驗證了 390px 下工作卡出現在第一個畫面、捲動時操作列固定且可點擊、結算可展開逐件漏件回顧，以及重開清空紀錄。`mobile-scrolled.png` 與 `result.png` 留存對應畫面。漏件快照測試涵蓋逾期、放棄與下班三種結案情況。

`npm run balance` 的 30 個種子（1～30）用每 0.5 秒決策的簡單策略檢查數值：

| 策略 | 平均交件 | 平均漏件 | 交件率 |
| --- | --- | --- | --- |
| 補電、降溫、優先最早期限 | 8.3 | 3.2 | 72% |
| 補電但不用風扇 | 3.1 | 8.1 | 28% |
| 使用風扇但不補電 | 2.0 | 9.2 | 18% |
| 全程只供電給電腦 | 2.0 | 9.2 | 18% |

第一種策略平均花 13.3 秒充電、26.2 秒降溫；28/30 局曾有兩件任務都只剩 15 秒內。這是程式策略的數值檢查，**不代表一般玩家必然達到這些分數，也不等於已驗證好玩或難度平衡**。

熱度測試另外驗證：工作比待機升溫快、斷電與待上傳採待機升溫、高溫下能搶交快完成的任務，以及在相同總時間內先降溫可增加長工作處理量。瀏覽器驗證 Q/W 切換與固定快捷鍵、新工作補空位、未接收工作不會誤選。

下一輪人工試玩建議觀察：

1. 能否一眼分辨「處理完成」與「真的交件」，上傳排隊是否造成有趣的取捨。
2. 補電與降溫的時機是否能判斷，是否有足夠餘裕而不用頻繁來回切換。
3. 中後段的重疊／急件是否讓優先順序值得思考，漏件是否可理解且願意再玩。

## 發布到 itch.io

1. 執行 `npm run build`。
2. 將 **dist 內的內容**壓成 ZIP，讓 `index.html` 在 ZIP 根目錄，保留 `assets`。
3. 上傳為 HTML 遊戲並設定瀏覽器內執行。建議桌機嵌入寬 1200、高 1000 以上，允許全螢幕；窄螢幕以直向捲動操作。

Vite 保留 `base: './'`，可在 itch.io 子目錄載入。請使用 `npm run preview` 或 itch.io，不要直接雙擊 HTML。
